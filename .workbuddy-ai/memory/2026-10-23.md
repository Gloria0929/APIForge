## 自动更新：脱离 Docker Hub（国内网络/白名单）

问题：版本检测打 `hub.docker.com/v2/repositories/.../tags`，更新用 `docker.pull` 直连 Hub；
国内不稳定，且镜像加速白名单会拒绝不在名单里的仓库（提示 not in whitelist）。

改造 `src/modules/version/version.service.ts`：
- 新增纯函数 `parseImageRef` / `withTag` / `repoPathOf` / `buildImageCandidates`，
  正确解析 `registry:5000/ns/repo:tag`，支持「完整镜像」与「仅注册中心前缀」两种备选写法。
- 版本检测优先级：`VERSION_MANIFEST_URL`（静态 JSON `{version,image}`，可放 OSS/CDN）

## 公开仓库的版本检测（人人可更新）

`registryBearerToken` 原本在没配 `DOCKER_REGISTRY_USERNAME/PASSWORD` 时直接返回 null，
导致公开仓库（如 ACR 公开仓库）的 tags 检测静默失败、别人收不到更新提示。
现改为：无凭证时也去换 token（不带 Authorization），符合 Registry V2 对公开仓库的匿名授权。

测试：`tests/version-update.test.cjs` 增至 12 个（新增匿名 token 用例，断言不带 Basic 头）。

发布策略（与用户沟通的结论）：
- 默认镜像仍指向 Docker Hub（`foehao09/apiforge`），外部用户行为不变；
- ACR 作为国内/自用加速渠道，需要"人人可拉"时必须把仓库设为**公开**；
- ACR 个人版地址含实例 ID（`crpi-xxx`），重建实例会变，不适合长期对外分发；
  大规模公开分发仍建议 Docker Hub 或 ACR 企业版。

## 直接拉镜像的用户如何跟随更新源

`Dockerfile` 里 `ARG DOCKER_IMAGE` + `ENV DOCKER_IMAGE=${DOCKER_IMAGE}`，
镜像构建时就把自己的仓库地址固化进环境变量，所以**拉哪个仓库的镜像，就从哪个仓库检查更新**：
推 ACR 的镜像启动的容器会自动查 ACR，无需用户配置。

之前 `docker-compose.yml` 里写死 `- DOCKER_IMAGE=${DOCKER_IMAGE:-foehao09/apiforge:latest}`，
会覆盖镜像内的值，导致用 compose 部署的人仍走 Hub。已改为注释掉，默认跟随镜像
（需要强制指定时再取消注释）。

限制：已在运行旧镜像的存量实例不会自动换仓库，必须手动 pull 新地址并重建一次；
自更新还要求容器挂载 `/var/run/docker.sock`，否则只能给出手动命令。

## ACR 推送报 unknown manifest class for application/vnd.oci.empty.v1+json

原因（已实测复现）：BuildKit 默认给多架构镜像附加 provenance/SBOM 证明，
产出的是 **OCI index**，其中两个 `platform: unknown/unknown` 的 attestation manifest
其 `config.mediaType` 正是 `application/vnd.oci.empty.v1+json`，ACR 个人版不认。

修复（`scripts/docker-push.sh`）：
```
--provenance="${PROVENANCE:-false}" --sbom=false \
--output "type=image,push=true,oci-mediatypes=${OCI_MEDIATYPES:-false}"
```
本地起 registry:2 实测对比：
- 默认参数 → `application/vnd.oci.image.index.v1+json`，4 个 manifest（2 平台 + 2 证明）
- 新参数 → `application/vnd.docker.distribution.manifest.list.v2+json`，仅 2 个平台 manifest，无 oci.empty

README 增「常见报错」两则（oci.empty / insufficient_scope）。

## 一键执行报「未解析的变量：token」

原因：`POST /api/tests/execute`（单条执行）第 5 个参数传 `useEnvironmentLogin=true`，
而 `executeTestSuite`（一键执行 / execute-suite）调 `executeTestCase(testCaseId, environmentId)`，
没传该参数 → 从不执行环境登录用例 → `{{token}}` 无处可来。

修复（`test.service.ts`）：在 `executeTestSuite` 开头调用一次
`resolveEnvironmentLoginVariables(undefined, environmentId, {})` 得到登录变量，
再作为 `extraVariables` 传给每个用例。只在开头解析一次，不会因并发/多用例重复登录。

实测：3 个用例（含登录用例本身）跑下来，登录接口共被调用 2 次（1 次预登录 + 登录用例自身），
两个业务请求都带上了 `Bearer tok-123`。
